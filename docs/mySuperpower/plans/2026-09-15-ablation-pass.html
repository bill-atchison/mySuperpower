Overview

Goal
Add an end-of-artifact ablation pass to the writing-plans, executing-plans and subagent-driven-development skills, through the fork’s overlay mechanism only.
Architecture
Each skill has an overlays/<skill>/additions.md that the build appends to the upstream SKILL.md. Three tasks, one per overlay, each appending a section whose wording is fixed in the spec. The build is the test harness: a section is present when its heading appears once in the built skill.
Tech Stack
Markdown, PowerShell 7 (scripts/build-mysuperpower.ps1), bash grep, git.

The text for each section is copied verbatim from the spec’s “The Text” section. The spec says the plan may tighten phrasing but not change the procedure; this plan does not tighten it, so the spec and the shipped text stay identical and one grep checks both.

Global Constraints

  • Touch only overlays/writing-plans/additions.md, overlays/executing-plans/additions.md, overlays/subagent-driven-development/additions.md. Nothing under skills/, no overlay.json, no scripts/.
  • Section headings use the fork’s existing form: ## mySuperpower additions — <topic> with an em dash, matching the headings already in each file.
  • Append at end of file, one blank line after the current last line. The build trims trailing whitespace and re-joins with a blank line, so file-end spacing does not affect output.
  • Files use LF line endings and no BOM, as the existing overlay files do. Write with a heredoc from bash, not from PowerShell, to keep that.
  • The dist/ directory is gitignored. Never git add it.

How the build proves each task

The build appends each overlay’s additions.md to the matching dist/skills/<skill>/SKILL.md. So the red–green cycle for prose is: grep the built skill for the new heading, see zero, append, rebuild, see one. Rebuilding takes about two seconds. The overlay test suite takes about twenty seconds and runs once per task before commit.

pwsh -NoProfile -File scripts/build-mysuperpower.ps1
grep -c "mySuperpower additions — <heading topic>" dist/skills/<skill>/SKILL.md
pwsh -NoProfile -File tests/mysuperpower/test-overlay-files.ps1

Baseline on this branch, measured before writing this plan: build exits 0 and prints skills=14; the grep returns 0 for all three skills; the overlay test prints overlay files tests passed.

## mySuperpower additions — ablation pass before finishing

After all tasks are complete and verified, and before invoking
finishing-a-development-branch, run one ablation pass over the branch:

1. List every abstraction the branch added: helpers, interfaces, base
   classes, config knobs, wrappers, layers, indirection of any kind.
2. For each one, replace it with the direct thing — inline the single-use
   helper, call the one implementation, write the never-changing value —
   and run the full test suite. Behavior stays; only the layer goes.
3. Name what failed: a test, a spec requirement, or a second caller that
   now has nothing to call. "It might be useful later" is not a failure.
4. If something failed, restore the abstraction and move on. If nothing
   failed, commit the removal.
5. Record each removal, and each restore with its reason, as a decision
   card in the implementation notes.

Run this once, at the end. Earlier tasks build scaffolding that later
tasks consume; ablating per task removes it before its consumer exists.
EOF

  2. Step 2: Confirm the shipped text matches the spec verbatim

    The spec’s three <pre><code> blocks are the source of truth. Extract each block from the spec, unescape HTML entities, and diff it against the tail of the built skill in dist/, which is what ships. Diffing the built file rather than the overlay source also proves the build’s rebrand cascade left the text alone. Zero diff lines means the plan changed nothing.

    SPEC=docs/mySuperpower/specs/2026-09-15-ablation-pass-design.html
unesc() { sed -e 's/&lt;/</g' -e 's/&gt;/>/g' -e 's/&amp;/\&/g' \
              -e 's/&ldquo;/"/g' -e 's/&rdquo;/"/g' -e "s/&rsquo;/'/g" -e 's/&hellip;/.../g'; }
block() { awk -v n="$1" '/<pre><code>/{c++} c==n{print} /<\/code><\/pre>/{if(c==n)exit}' "$SPEC" \
  | sed -e '1s/^<pre><code>//' -e '$s/<\/code><\/pre>$//' | unesc; }
shipped() { sed -n "/^## mySuperpower additions — $2/,\$p" "dist/skills/$1/SKILL.md"; }
diff <(block 1) <(shipped writing-plans "Self-Review, item 4") && echo WP-OK
diff <(block 2) <(shipped executing-plans "ablation pass before finishing") && echo EP-OK
diff <(block 3) <(shipped subagent-driven-development "ablation pass before the final review") \
  && echo SDD-OK

    Expected: WP-OK, EP-OK, SDD-OK, no diff output. If a diff appears, the overlay is wrong, not the spec: fix the overlay, rebuild, and rerun. The build writes the appended section as the last thing in each file, so the sed range runs to end of file.

Risks

RiskMitigation
Heredoc written from PowerShell adds CRLF or a BOM, and the built skill ships mixed line endings.Global constraint: use bash heredocs. Task 4 Step 2 diffs the overlay tail against the spec, and CRLF shows as a diff.
Em dash in the heading typed as a hyphen, so the grep pattern misses it.The heredocs carry the em dash literally. The grep pattern in every step uses the same character. A 0 in Step 3 of any task means the heading is wrong.
Section appended to the wrong overlay.Task 4 Step 1 counts per-file and total. A file at 2 or a total above 3 fails.
The build’s rebrand cascade rewrites a word inside the new text.The cascade rewrites superpowers: namespaces and docs/superpowers/ paths. The new text contains neither. Task 4 Step 2 diffs the built skill against the spec, so any rewrite shows as a diff.
