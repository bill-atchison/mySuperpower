HTML Task Briefs for Subagent-Driven Development

Teach the SDD brief pipeline to read the fork’s HTML plans — without touching one byte of upstream.

Date
2026-08-29
Branch

Design — Awaiting Plan + Impl
Source
The fork’s writing-plans skill emits HTML plans; SDD’s task-brief only parses markdown headings, so every dispatch on a fork plan fails.

Overview

mySuperpower’s writing-plans overlay writes implementation plans as self-contained HTML into docs/mySuperpower/plans/. Its subagent-driven-development skill still reaches for upstream’s markdown tooling to read them. The two halves of the fork disagree about what a plan is.

Four things break, in descending order of severity.

1. task-brief cannot find a task

skills/subagent-driven-development/scripts/task-brief selects a task with awk, on a markdown heading:

!infence && /^#+[ \t]+Task[ \t]+[0-9]+/ {
    intask = ($0 ~ ("^#+[ \t]+Task[ \t]+" n "([^0-9]|$)"))
}

An HTML plan writes the same idea as <section class="task"><h3>Task 1 — Title</h3>. Nothing matches, the output file is empty, and the script exits 3. This is a hard stop before the first implementer is ever dispatched.

2. Escaped entities become wrong source code

Plan code samples live in <pre><code>, so <meta> is stored as &lt;meta&gt;. SKILL.md introduces the brief to the implementer as “your requirements, with the exact values to use verbatim.” A brief carrying raw markup asks a subagent to take the escaped form literally.

What raw extraction hands over

strip the &lt;meta ... refresh&gt; tag

What the code has to say

strip the <meta ... refresh> tag

3. The controller ingests the stylesheet

SDD setup instructs the controller to read the plan once. The fork’s plans open with roughly sixty lines of inline CSS before any content — 2026-06-21-live-implementation-notes.html is 20 KB, most of it presentation the controller has no use for.

4. Briefs carry no provenance

task-brief overwrites task-N-brief.md with no record of which plan revision produced it. The fork’s browser acceptance gate actively invites revising a plan mid-run, and the same brief is later handed to the task reviewer and the re-reviewer — who then judge the work against requirements that may no longer exist.

Chosen Approach

Ship a fork-owned extractor as an overlay asset, and extend the build with a general overlay files capability that copies fork-owned files into dist/skills/<skill>/. Upstream’s task-brief, sdd-workspace and review-package are not edited, patched, or wrapped.

This follows the architecture the fork already committed to: the git-tracked source tree stays pristine, and every mySuperpower transform happens at build time. Today an overlay can rewrite and append to SKILL.md and nothing else; files is the missing third verb, and it is reusable by every future overlay.

Alternatives considered

OptionWhy not
Anchor-patch upstream’s task-brief at build time Puts fork anchors inside an upstream script. Any upstream rework of that awk block fails the build until the anchor is refit — a recurring merge tax paid to avoid one new file.
Instructions only, no script Moves deterministic text transformation into the controller’s context on every single task, and makes correct entity decoding a matter of model attention rather than code.
Emit markdown plans alongside HTML Two artifacts drift. The HTML plan is the reviewed and signed-off artifact; a shadow copy would quietly become the real one.

Architecture

One fact drives every integration hazard below: a fork-owned file’s source path is not its published path. The build renames it on the way into dist/, and every tool that reasons about files by path has to cross that gap.

overlays/subagent-driven-development/scripts/task-brief-html
→
skills/subagent-driven-development/scripts/task-brief-html
Source lives beside the overlay that owns it; the build copies it into the skill.
dist/skills/…/scripts/task-brief-html
→
release:skills/…/scripts/task-brief-html
release:plugins/my-superpower/skills/…/scripts/task-brief-html
Publish writes the plugin twice — branch root for Claude Code, subdirectory for Codex.

Build: the files capability

scripts/build-mysuperpower.ps1 gains a step inside its existing overlay loop. For each entry in an overlay’s files array, copy <overlayDir>/<from> to dist/skills/<skill>/<to>, creating intermediate directories.

{
  "skill": "subagent-driven-development",
  "replaces": [],
  "append": "additions.md",
  "files": [
    { "from": "scripts/task-brief-html", "to": "scripts/task-brief-html" }
  ]
}

A missing from is a fail-loud build error, matching how a missing required anchor already behaves — loud failure at build time is the property that makes the overlay system trustworthy. The build’s verification step gains one assertion: every declared to exists in dist/.

That assertion is not ceremony. The current checks are the dist plugin name, the skill count, and residual superpowers: references. A silently skipped copy passes all three while shipping a SKILL.md that tells the controller to run a script which is not there.

Hazard 1 — the executable bit

scripts/publish-mysuperpower.ps1 restores +x by reading git ls-files -s on the source repo and looking for each 100755 path in the release tree, at the root and under plugins/my-superpower/. Its own comment notes that deriving the list means “a new upstream executable is covered with no change to this script.” A new fork executable is not: its source path is overlays/…, which is excluded from dist/ and therefore matches neither target.

The script would publish as 100644 and die with Permission denied on macOS and Linux — the exact failure 6.2.0+fork.2 fixed, re-entering through a new door.

Fix: publish reads each overlays/*/overlay.json, and for every files entry whose source blob is 100755 in the index, chmods the published path in both copies. The same principle the existing block documents — the index is the only signal that survives Windows — applied across the rename.

Hazard 2 — line endings

.gitattributes pins *.sh, hooks/session-start and *.cmd to LF. The SDD scripts are extensionless and match none of those rules. Their working-tree copies are CRLF on a Windows checkout, dist/ inherits CRLF, and only core.autocrlf normalizing inside the publish worktree makes the released blob LF. It holds today by side effect; a publishing machine with core.autocrlf=false would ship a CR-terminated shebang and every script would fail to start.

Fix: add two rules to .gitattributes:

skills/**/scripts/*   text eol=lf
overlays/**/scripts/* text eol=lf

Both are required. The first covers the new script and the three existing ones at their published location; the second covers the fork script at its source location, which is where the build copies from — a rule on skills/ alone would let a CRLF working-tree copy flow straight into dist/. The fork already appends its own merge=ours rule to this file, so a fork-owned line here has precedent.

Components

Command contract

task-brief-html PLAN_FILE TASK_NUMBER [OUTFILE]   # default <workspace>/task-N-brief.md
task-brief-html --overview PLAN_FILE [OUTFILE]    # default <workspace>/plan-overview.md

Deliberately congruent with upstream’s task-brief: same argument order, same default output location, same exit codes, same closing line printing the path it wrote. The controller’s only branch is on the plan’s file extension.

Written in bash and awk, matching every other script in the skill, so SDD’s dependency set stays bash plus git.

Workspace resolution

The script calls upstream sdd-workspace unmodified. That leaves the directory named <plan-basename>.html/, because basename "$plan" .md does not strip .html. This is cosmetic and is deliberately not fixed: every caller passes the same PLAN_FILE, so briefs, review packages and the progress ledger all resolve to one directory. A prettier slug in one script would split the workspace and strand the ledger — the exact failure the plan-scoped workspace was introduced to prevent.

Task selection, layered

Real fork plans do not agree on class names. 2026-05-25 uses class="step", 2026-06-21 uses class="s", and 2026-06-19 has no task sections at all. Selection keys on structure, with class names as a hint only:

  1. Preferred: a <section> carrying class="task", closed by its matching </section>, whose heading text matches Task <N>.
  2. Fallback: any <h2> or <h3> whose text matches Task <N>, extracting to the next heading of the same or higher level. This mirrors upstream’s own heading-delimited strategy and survives arbitrary section markup.
  3. Neither: exit 3, the same code and the same message shape upstream uses for a missing task.

Conversion rules

  • <pre><code> becomes a fenced block; entities decoded, no tag stripping inside.
  • <li> inside <ol> becomes a numbered step; inside <ul>, a dash. A files block becomes a plain Files list.
  • Block-level tags become line breaks; inline tags (strong, em, span, code) are dropped and their text kept.
  • Entities decoded: &lt;, &gt;, &quot;, &#39;, &mdash;, &nbsp;, numeric forms, and &amp; last — so &amp;lt; decodes to &lt; and not to <.
  • Runs of blank lines collapse to one. The brief is read by a subagent, not rendered.

Overview mode

--overview runs the same converter over the Overview and Global Constraints sections plus an index of every task heading, and emits nothing from <head> — which is where the CSS lives. It replaces the controller’s whole-file plan read at setup.

Provenance header

Every brief opens with three lines: source plan path, plan content hash from git hash-object, and extraction timestamp. There is deliberately no comparison or invalidation logic — there is no stored state to compare against, and inventing one would be machinery this problem has not asked for. The header exists so a human reading a brief can see it predates a plan revision.

Overlay instruction text

overlays/subagent-driven-development/additions.md gains a scoped override: when PLAN_FILE ends in .html, use scripts/task-brief-html everywhere the skill says scripts/task-brief, and read the plan with --overview at setup rather than whole. Scoped the same way the brainstorming overlay is scoped to the architectural path, so a markdown plan still follows upstream exactly.

Error Handling

The script’s failure modes match upstream’s, so the controller needs no new handling. The build and publish failures are loud by design — the whole value of the overlay architecture is that a fork assumption which stopped being true stops the build rather than shipping quietly.

ConditionBehaviorCode
Wrong argument countUsage message on stderr2
Plan file missingno such plan file: <path>2
Task N not found by either strategyNames the plan and the task number; writes no partial brief3
Unbalanced markup in the selected sectionExtracts to the next task heading and warns on stderr; the brief is still written0
Overlay declares a files entry that is missingBuild fails, naming the overlay and the pathbuild
Declared files target absent from dist/Build verification failsbuild
Fork script published without +xPublish fails on the chmod it could not applypublish

The unbalanced-markup row is the one soft failure. An LLM-authored plan with a stray unclosed tag should still yield a usable brief; truncating at the next task boundary with a warning beats refusing to dispatch.

Testing

Fork-owned, under tests/mysuperpower/ — upstream’s tests/ are not maintained in this fork, and these cover fork-owned code.

tests/mysuperpower/test-task-brief-html.sh

Against dedicated committed fixtures under tests/mysuperpower/fixtures/ — plan-sections.html (three tasks in <section class="task">) and plan-headings.html (tasks as bare headings, no task class) — so the assertions stay stable as the real plans age:

  • Task 2 of 3 extracts with its own heading, steps and code, and nothing from tasks 1 or 3.
  • &lt;meta&gt; in the plan arrives as <meta> in the brief; &amp;lt; arrives as &lt;.
  • Fenced code blocks survive intact, including indentation.
  • A missing task exits 3 and writes no brief.
  • The fallback selector finds a task in a fixture with no class="task".
  • --overview output contains the goal text and no CSS rules.
  • The provenance header names the plan and its hash.

Plus one smoke run against the real docs/mySuperpower/plans/2026-06-21-live-implementation-notes.html, asserting a non-empty brief for Task 1 — cheap protection against a fixture that has drifted from what the template actually produces.

Build capability test

Assert that a declared files entry lands at its declared to path in dist/, and that a declared-but-missing source fails the build. Runs after build-mysuperpower.ps1, alongside the existing dist checks.

Manual verification before release

  1. Build; confirm dist/skills/subagent-driven-development/scripts/task-brief-html exists.
  2. Publish locally; confirm the release blob is 100755 in both copies and the file is LF.
  3. Run the extractor against a real fork plan and read the brief end to end.

Out of Scope

  • Out executing-plans parity. That skill has no brief step; only --overview would apply. Once files exists, adding it is a few lines — deferred until wanted.
  • Out Fixing the .html workspace directory name. Cosmetic, and any fix not applied to every caller splits the workspace.
  • Out Brief invalidation or staleness enforcement. Provenance is recorded; comparison logic is not built.
  • Out A general HTML-to-markdown converter. The extractor targets the fork’s own plan template, and fails loud rather than guessing at arbitrary HTML.
  • Out Any change to upstream’s task-brief, sdd-workspace, or review-package.
