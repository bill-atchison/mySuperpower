HTML Task Briefs for Subagent-Driven Development

Teach the SDD brief pipeline to read the fork’s HTML plans — without touching one byte of upstream.

Source
The fork’s writing-plans skill emits HTML plans; SDD’s task-brief only parses markdown headings, so every dispatch on a fork plan fails.

Overview

mySuperpower’s writing-plans overlay writes implementation plans as self-contained HTML into docs/mySuperpower/plans/. Its subagent-driven-development skill still reaches for upstream’s markdown tooling to read them. The two halves of the fork disagree about what a plan is.

Four things break, in descending order of severity.

1. task-brief cannot find a task

skills/subagent-driven-development/scripts/task-brief selects a task with awk, on a markdown heading:

!infence && /^#+[ \t]+Task[ \t]+[0-9]+/ {
    intask = ($0 ~ ("^#+[ \t]+Task[ \t]+" n "([^0-9]|$)"))
}

An HTML plan writes the same idea as <section class="task"><h3>Task 1 — Title</h3>. Nothing matches, the output file is empty, and the script exits 3. This is a hard stop before the first implementer is ever dispatched.

2. Escaped entities become wrong source code

Plan code samples live in <pre><code>, so <meta> is stored as &lt;meta&gt;. SKILL.md introduces the brief to the implementer as “your requirements, with the exact values to use verbatim.” A brief carrying raw markup asks a subagent to take the escaped form literally.

What raw extraction hands over

strip the &lt;meta ... refresh&gt; tag

What the code has to say

strip the <meta ... refresh> tag

3. The controller reads the plan through its stylesheet

SDD setup instructs the controller to read the plan once. It reads the presentation layer along with it: the <head> of 2026-06-21-live-implementation-notes.html is about 4 KB of the file’s 20 KB, and presentational markup runs through the body on top of that. Not fatal — but it is pure noise on the one read the whole run is planned from.

4. Briefs carry no provenance

task-brief overwrites task-N-brief.md with no record of which plan revision produced it. The fork’s writing-plans overlay ends with “open the .html in the user’s browser for an acceptance gate and get sign-off” — a gate whose whole purpose is to send a plan back for revision. The same brief is later handed to the task reviewer and the re-reviewer, who then judge the work against requirements that may no longer exist.

Chosen Approach

Ship a fork-owned extractor as an overlay asset, and extend the build with a general overlay files capability that copies fork-owned files into dist/skills/<skill>/. Upstream’s task-brief, sdd-workspace and review-package are not edited, patched, or wrapped.

This follows the architecture the fork already committed to: the git-tracked source tree stays pristine, and every mySuperpower transform happens at build time. Today an overlay can rewrite and append to SKILL.md and nothing else; files is the missing third verb, and it is reusable by every future overlay.

Alternatives considered

OptionWhy not
Anchor-patch upstream’s task-brief at build time Puts fork anchors inside an upstream script. Any upstream rework of that awk block fails the build until the anchor is refit — a recurring merge tax paid to avoid one new file.
Instructions only, no script Moves deterministic text transformation into the controller’s context on every single task, and makes correct entity decoding a matter of model attention rather than code.
Emit markdown plans alongside HTML Two artifacts drift. The HTML plan is the reviewed and signed-off artifact; a shadow copy would quietly become the real one.

Architecture

One fact drives every integration hazard below: a fork-owned file’s source path is not its published path. The build renames it on the way into dist/, and every tool that reasons about files by path has to cross that gap.

overlays/subagent-driven-development/scripts/task-brief-html
→
skills/subagent-driven-development/scripts/task-brief-html
Source lives beside the overlay that owns it; the build copies it into the skill.
dist/skills/…/scripts/task-brief-html
→
release:skills/…/scripts/task-brief-html
release:plugins/my-superpower/skills/…/scripts/task-brief-html
Publish writes the plugin twice — branch root for Claude Code, subdirectory for Codex.

Build: the files capability

scripts/build-mysuperpower.ps1 gains a step inside its existing overlay loop. For each entry in an overlay’s files array, copy <overlayDir>/<from> to dist/skills/<skill>/<to>, creating intermediate directories.

{
  "skill": "subagent-driven-development",
  "replaces": [],
  "append": "additions.md",
  "files": [
    { "from": "scripts/task-brief-html", "to": "scripts/task-brief-html", "exec": true }
  ]
}

The files key is optional, and “optional” has teeth here: build-mysuperpower.ps1:19 sets Set-StrictMode -Version Latest, under which reading a property that does not exist on a ConvertFrom-Json object throws rather than returning null. Every overlay.json in the repo today carries both replaces and append for exactly this reason. The new step must probe with $cfg.PSObject.Properties.Name -contains 'files', not if ($cfg.files), so existing overlays keep building untouched.

An overlay without files behaves exactly as today. exec defaults to false and declares that the published file must be executable — see the publish hazard below, where making that intent explicit is what turns a silent regression into a failed release.

Schema rules, enforced at build time

Every rule below fails the build loudly, naming the overlay and the entry. Loud failure at build time is the property that makes the overlay system trustworthy, and an unvalidated copy step is a file-write primitive pointed at the build output.

  • from and to are relative paths. Absolute paths and any .. segment are rejected outright, not normalized.
  • from must resolve inside the overlay’s own directory and be an existing regular file — not a directory, not a symlink.
  • to must resolve inside dist/skills/<skill>/.
  • to must not already exist in dist/. An overlay silently replacing an upstream file would be a source-patching mechanism wearing a copy step’s clothes, and the fork has deliberately refused that.
  • No two entries may resolve to the same canonical destination, dist/skills/<skill>/<to>. The comparison is on the resolved path, not the raw to string: two overlays for different skills may both legitimately ship scripts/helper, and those are different files.
  • exec, when present, must be a JSON boolean. Absent means false.

The build’s verification step then asserts every declared to exists in dist/. That assertion is not ceremony: the current checks are the dist plugin name, the skill count, and residual superpowers: references. A silently skipped copy passes all three while shipping a SKILL.md that tells the controller to run a script which is not there.

Hazard 1 — the executable bit

scripts/publish-mysuperpower.ps1 restores +x by reading git ls-files -s on the source repo and looking for each 100755 path in the release tree, at the root and under plugins/my-superpower/. Its own comment notes that deriving the list means “a new upstream executable is covered with no change to this script.” A new fork executable is not: its source path is overlays/…, which is excluded from dist/ and therefore matches neither target.

The script would publish as 100644 and die with Permission denied on macOS and Linux — the exact failure 6.2.0+fork.2 fixed, re-entering through a new door.

Fix: publish reads each overlays/*/overlay.json and, for every files entry marked "exec": true, chmods the published path in both copies. The same principle the existing block documents — the index is the only signal that survives Windows — applied across the rename.

The intent has to be declared rather than sniffed from the source mode. If publish only chmodded files it found at 100755 in the index, then a source file committed 100644 by accident — the single most likely way this goes wrong, since Windows checkouts have no mode bit to preserve — would produce no chmod, no error, and a broken release. With exec: true declared, publish fails when the source is not 100755 in the index, naming the file and the git update-index --chmod=+x that fixes it.

Hazard 2 — line endings

.gitattributes pins *.sh, hooks/session-start and *.cmd to LF. The SDD scripts are extensionless and match none of those rules. Their working-tree copies are CRLF on a Windows checkout, dist/ inherits CRLF, and only core.autocrlf normalizing inside the publish worktree makes the released blob LF. It holds today by side effect; a publishing machine with core.autocrlf=false would ship a CR-terminated shebang and every script would fail to start.

Fix: add two rules to .gitattributes:

skills/**/scripts/*   text eol=lf
overlays/**/scripts/* text eol=lf

Both are required. The first covers the new script and the three existing ones at their published location; the second covers the fork script at its source location, which is where the build copies from — a rule on skills/ alone would let a CRLF working-tree copy flow straight into dist/. The fork already appends its own merge=ours rule to this file, so a fork-owned line here has precedent.

Components

Command contract

task-brief-html PLAN_FILE TASK_NUMBER [OUTFILE]   # default <workspace>/task-N-brief.md
task-brief-html --plan PLAN_FILE [OUTFILE]        # default <workspace>/plan-body.md

Congruent with upstream’s task-brief: same argument order, same default output location, same exit codes, same closing line printing the path it wrote. The controller’s only branch is on the plan’s file extension.

One behavior differs from upstream deliberately. Upstream redirects awk into the output file and only then tests whether it is empty, so a missing task leaves a zero-byte task-N-brief.md behind (task-brief:34-38). This script writes to a temp file in the output directory — same filesystem, so the rename is atomic — and renames it into place only on success. A half-written brief is the worst possible artifact here: it looks like requirements.

Temp-and-rename alone is not enough, and the gap is worth naming. Briefs are re-extracted after a plan revision, so a failed extraction that merely declines to write would leave the previous successful brief sitting at the expected path, looking current, with nothing to distinguish it. On any failure the script therefore deletes the target path before exiting 3. A missing brief stops the controller; a stale one silently misdirects it.

That deletion is scoped to the default workspace path, which the script owns and which holds nothing but generated briefs. When OUTFILE is given explicitly the script deletes nothing — it exits 3 and names the path as possibly holding a stale brief. A tool that removes a file the caller named is a tool that eventually removes the wrong one.

Written in bash and awk, matching every other script in the skill and adding no new dependency — upstream’s task-brief already uses awk, wc and tr.

Workspace resolution

The script calls upstream sdd-workspace unmodified. That leaves the directory named <plan-basename>.html/, because basename "$plan" .md does not strip .html. This is cosmetic and is deliberately not fixed: every caller passes the same PLAN_FILE, so briefs, review packages and the progress ledger all resolve to one directory. A prettier slug in one script would split the workspace and strand the ledger — the exact failure the plan-scoped workspace was introduced to prevent.

Task selection, layered

Real fork plans disagree about how a task is identified, and the difference is not cosmetic. 2026-06-21 writes <section class="task"><h3>Task 1 — Title</h3>. 2026-05-25 writes <section class="task"><h2>Wire the upstream remote &amp; record baseline</h2> — no task number in the heading at all, at a different heading level. There, task identity is positional. 2026-06-19 has no task sections at all. The plan template mandates section.task but never mandates that the heading name a number.

Selection therefore keys on structure, in this order:

  1. Positional, preferred. If the plan contains <section class="task"> elements, task N is the Nth such section in document order, closed by its matching </section> with nesting tracked.
  2. Cross-check. Take the section’s first heading element in document order within that section. If its text names a task number and that number is not N, exit 3 naming both. Position and label disagreeing means the plan is mis-numbered; guessing which one the controller meant is exactly the silent wrong answer this design must not produce. A heading with no number is not a conflict — that is the 2026-05-25 shape, and position governs.
  3. Fallback. If there are no task sections, select on any heading whose text matches Task <N>, extracting to the next heading that matches Task <any number> at any level — the same boundary rule upstream’s awk uses, which flips on any Task heading regardless of depth.
  4. Neither yields a task: exit 3.

Conversion rules

  • <pre><code> becomes a fenced block; entities decoded, no tag stripping inside.
  • The fence must be longer than the longest backtick run in the payload (scan first, use that run + 1, minimum 3). Plan code blocks really do contain fences: 2026-05-25-mysuperpower-conversion.html:510-534,580-586 holds triple-backtick markdown samples inside <pre><code>, because that task writes a README. A fixed ``` fence would let the inner fence close the outer one, spilling the rest of the payload into prose — a brief that looks complete while silently reclassifying requirements as commentary.
  • <li> inside <ol> becomes a numbered step; inside <ul>, a dash. A files block becomes a plain Files list.
  • Block-level tags become line breaks; inline tags (strong, em, span, code) are dropped and their text kept.
  • Entities decoded from a named table — at minimum lt gt quot apos nbsp mdash ndash hellip middot rarr larr lsquo rsquo ldquo rdquo times — plus numeric decimal and hex forms, with &amp; decoded last so &amp;lt; becomes &lt; and not <. The table must cover what the plan template itself emits: it writes &middot; and &rarr; today.
  • Any &name; the table does not cover is left as-is and warned about on stderr, naming the entity. An enumerated list will fall behind the template eventually; the warning is what keeps that drift visible instead of quietly shipping &middot; into a subagent’s requirements.
  • Runs of blank lines collapse to one. The brief is read by a subagent, not rendered.

Plan mode

--plan renders the entire plan body — Overview, Global Constraints, and every task in full — through the same converter, emitting nothing from <head>.

It renders the whole body, not a summary, because of what SDD setup actually requires. SKILL.md:163-180 mandates a pre-flight conflict scan whose output is a table with one row for every pair of tasks that share a file or an interface — what one produces against what the other consumes — plus one row per task checking its own text against itself. That scan needs every task’s full body. An overview-only extract would quietly starve it, and a controller cannot tell the difference between a clean scan and a scan run on missing input.

The saving is therefore modest and honest: the <head> stylesheet is about 4 KB of the 20 KB 2026-06-21 plan, and presentational markup accounts for more throughout the body. What --plan removes is noise, not content.

Provenance header

Every brief opens with three lines: source plan path, plan content hash from git hash-object, and extraction timestamp. There is deliberately no comparison or invalidation logic — there is no stored state to compare against, and inventing one would be machinery this problem has not asked for. The header exists so a human reading a brief can see it predates a plan revision.

Overlay instruction text

overlays/subagent-driven-development/additions.md gains a scoped override: when PLAN_FILE ends in .html, use scripts/task-brief-html everywhere the skill says scripts/task-brief, and read the plan with --plan at setup rather than opening the .html directly. Scoped the same way the brainstorming overlay is scoped to the architectural path, so a markdown plan still follows upstream exactly.

Stale Call Sites the Cascade Cannot Fix

The build’s rebrand cascade rewrites docs/superpowers/ to docs/mySuperpower/ and never touches the extension. Upstream’s markdown examples therefore ship with fork paths and markdown suffixes — a path shape that cannot exist in this fork. Two of them matter, and both are fixed with overlay replaces entries.

Anchors match pristine text, not branded text

Overlays are step 4 of the build; the cascade is step 5 (build-mysuperpower.ps1:47,76). An anchor must therefore match the upstream string — docs/superpowers/… — and its replacement should keep that prefix and change only the extension, leaving the cascade to rebrand it afterwards. An anchor written against docs/mySuperpower/ matches nothing and fails the build.

The SDD worked example

subagent-driven-development/SKILL.md:509-510 is the transcript a controller pattern-matches at setup, and it demonstrates both behaviors this design replaces — reading the plan whole, and handing a .md path to the workspace resolver:

find:    [Read plan file once: docs/superpowers/plans/feature-plan.md]
replace: [Read plan body once: scripts/task-brief-html --plan docs/superpowers/plans/feature-plan.html]

find:    scripts/sdd-workspace docs/superpowers/plans/feature-plan.md
replace: scripts/sdd-workspace docs/superpowers/plans/feature-plan.html

Both required: true. If upstream rewords the worked example, the fork should find out at build time rather than ship a transcript teaching the wrong tool.

The code-review dispatch example

requesting-code-review/SKILL.md:60 names the artifact the final reviewer is pointed at. That skill has no overlay today, so this adds overlays/requesting-code-review/ — an overlay.json with one replaces entry, an empty files array, and no append file:

find:    docs/superpowers/plans/deployment-plan.md
replace: docs/superpowers/plans/deployment-plan.html

It is worth adding for its own sake, and it doubles as the first proof that a second overlay composes — the collision rule compares canonical dist/skills/<skill>/<to> paths precisely so two overlays can coexist without colliding on identical relative names.

The workspace artifacts stay markdown and are not migrated: progress.md, task-N-brief.md, task-N-report.md and the review .diff live in .superpowers/sdd/, are read by subagents rather than by a human in a browser, and are easier to grep and diff as text. Migrating them would cost the fork something and buy it nothing.

Error Handling

The script’s failure modes match upstream’s, so the controller needs no new handling. The build and publish failures are loud by design — the whole value of the overlay architecture is that a fork assumption which stopped being true stops the build rather than shipping quietly.

ConditionBehaviorCode
Wrong argument countUsage message on stderr2
Plan file missingno such plan file: <path>2
Task N not found by either strategyNames the plan and the task number; deletes an existing brief at the default path, never at an explicit OUTFILE3
Section position and heading number disagreeNames both numbers; same deletion rule as above — default path only, never an explicit OUTFILE3
Named entity outside the decode tableLeft as-is, named on stderr; the brief is still written0
Unbalanced markup in the selected sectionExtracts to the next task boundary and warns on stderr; the brief is still written0
files entry names a missing, absolute, escaping, or non-regular fromBuild fails, naming the overlay and the entrybuild
to escapes the skill dir, collides with another entry, or already exists in dist/Build fails, naming the overlay and the entrybuild
Declared files target absent from dist/Build verification failsbuild
exec: true entry whose source is not 100755 in the indexPublish fails, naming the file and the git update-index fixpublish

The unbalanced-markup row is the one soft failure. An LLM-authored plan with a stray unclosed tag should still yield a usable brief; truncating at the next task boundary with a warning beats refusing to dispatch.

Testing

Fork-owned, under tests/mysuperpower/ — upstream’s tests/ are not maintained in this fork, and these cover fork-owned code.

tests/mysuperpower/test-task-brief-html.sh

Against dedicated committed fixtures rather than the real plans, so the assertions stay stable as those plans age:

  • Task 2 of 3 extracts with its own heading, steps and code, and nothing from tasks 1 or 3.
  • &lt;meta&gt; in the plan arrives as <meta> in the brief; &amp;lt; arrives as &lt;.
  • Fenced code blocks survive intact, including indentation.
  • Embedded fences: a task whose <pre><code> payload contains its own ``` block is wrapped in a longer fence, and the payload round-trips whole. The fixture uses the real shape from 2026-05-25-mysuperpower-conversion.html.
  • A missing task exits 3 and leaves no file at all — not an empty one, and not a previously extracted brief: the test writes a good brief first, then re-extracts a missing task and asserts the path is gone.
  • Explicit OUTFILE is never deleted: point both failure modes — missing task and position/label conflict — at an existing caller-owned file and assert it survives byte-for-byte.
  • Positional selection: in plan-unnumbered.html, whose task sections carry plain <h2> headings with no task number (the 2026-05-25 shape), task 2 returns the second section.
  • Position/label conflict: a fixture whose second section is headed “Task 3” exits 3 naming both numbers.
  • Fallback selection: plan-headings.html, with no task sections at all, selects on the heading and stops at the next Task heading of any level.
  • --plan output contains every task’s body and no CSS rules.
  • The provenance header names the plan and its hash.

Fixtures live in tests/mysuperpower/fixtures/: plan-sections.html (numbered task sections), plan-unnumbered.html (sections, unnumbered headings), plan-headings.html (headings only), plan-conflict.html (position and label disagree).

Plus one smoke run against the real docs/mySuperpower/plans/2026-06-21-live-implementation-notes.html, asserting a non-empty brief for Task 1 — cheap protection against a fixture that has drifted from what the template actually produces.

Build capability test

Assert that a declared files entry lands at its declared to path in dist/, that an overlay with no files key still builds under Set-StrictMode -Version Latest, and that each schema rule fails the build: a missing from, an absolute path, a .. segment in either field, a to that already exists in dist/, and two entries resolving to the same canonical destination. An unrecognized named entity must warn without failing. Runs after build-mysuperpower.ps1, alongside the existing dist checks.

One publish-side assertion too, since this is where the regression would land silently: with exec: true declared and the source committed 100644, the publish must fail rather than ship.

Call-site assertions

After a build, assert that dist/ contains no occurrence of docs/mySuperpower/ followed by a path ending in .md. That single check covers both migrated call sites and catches the next one an upstream merge introduces, which is the failure mode worth guarding — the cascade will keep manufacturing these silently.

Manual verification before release

  1. Build; confirm dist/skills/subagent-driven-development/scripts/task-brief-html exists.
  2. Publish locally; confirm the release blob is 100755 in both copies and the file is LF.
  3. Run the extractor against a real fork plan and read the brief end to end.

Out of Scope

  • Out executing-plans parity. That skill has no brief step; only --plan would apply. Once files exists, adding it is a few lines — deferred until wanted.
  • Out Fixing the .html workspace directory name. Cosmetic, and any fix not applied to every caller splits the workspace.
  • Out Brief invalidation or staleness enforcement. Provenance is recorded; comparison logic is not built.
  • Out A general HTML-to-markdown converter. The extractor targets the fork’s own plan template, and fails loud rather than guessing at arbitrary HTML.
  • Out Any change to upstream’s task-brief, sdd-workspace, or review-package.
