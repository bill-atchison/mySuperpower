Ablation Pass for Plans and Implementation

Turn “YAGNI” from a value into a step: delete each abstraction, see what fails, keep only what something needs.

Date
2026-09-15
Branch
feature/ablation-pass
Status
Design — Awaiting Plan + Impl
Source
Owner proposal: “after finishing the design or implementation each time, conduct an ablation experiment, removing unnecessary abstractions and designs.”

Overview

The skills already hold the principle. Brainstorming says “YAGNI ruthlessly”, writing-plans says “DRY. YAGNI. TDD.” in its intro, and the subagent-driven implementer and reviewer prompts each carry an over-building check per task. What none of them has is a procedure run at the end, over the whole artifact, that asks a checkable question. The writing-plans Self-Review lists three concrete checks (spec coverage, placeholders, type consistency) and nothing about excess design. Executing-plans goes from “all tasks verified” straight to finishing-a-development-branch. Subagent-driven development checks each task in isolation and never looks at the branch as a whole, where scaffolding built for Task 2 and abandoned by Task 5 lives.

This spec adds one ablation pass to each of those three places. The pass is the same question asked at three points: for each abstraction introduced, replace it with the direct thing and name what fails. If nothing fails, it goes.

“Remove” means replace indirection, not delete behavior. A single-use helper is inlined at its caller. An interface with one implementation is replaced by that implementation. A config knob for a value that never changes becomes the value. A wrapper that adds nothing becomes a call to what it wrapped. The behavior the abstraction carried survives; only the layer goes. The same definition applies in all three skills.

Chosen Approach

Inline text in the three fork overlays. Each of overlays/writing-plans/additions.md, overlays/executing-plans/additions.md and overlays/subagent-driven-development/additions.md gains a short section, worded for that skill’s position in the flow. The build script already appends these files to the published skills, so nothing in scripts/, overlay.json or tests/ needs to change.

Rejected: a single shared ablation-pass.md copied into all three skills. It removes about twenty lines of duplication at the cost of a build-script change and a fork-owned-file entry in three manifests. Not worth it.

Rejected: editing the upstream files under skills/. The project guidelines require eval evidence for behavior-shaping changes to upstream skill content, and the fork keeps its changes in overlays so upstream merges stay clean.

Placement

The pass runs once, at the end, in every skill. Per-task ablation was considered and rejected: early tasks in a plan build helpers and types that later tasks consume, and a per-task pass would delete them before their consumer exists.

writing-plans

Where
Fourth item in the existing Self-Review checklist, after Type consistency, before Execution Handoff.
What it deletes
Abstractions the plan introduces that no task requires: helpers, interfaces, base classes, config knobs, wrappers, layers.
What must survive
Every spec requirement still maps to a task. The plan still names concrete files and code.

executing-plans

Where
Between “all tasks complete and verified” (Step 3) and the finishing-a-development-branch handoff.
What it deletes
Abstractions the branch added that no test, spec requirement, or second caller depends on.
What must survive
The full test suite, green, after each deletion. Each deletion recorded as a decision card in the live implementation notes.

subagent-driven-development

Where
After every task’s ledger line reads complete, including complete (… parked) after a tripped breaker, and before the final review package is generated, so the final reviewer sees the ablated branch. The package script diffs MERGE_BASE..HEAD, so ablation commits must land first.
Who runs it
The controller, directly. No new subagent. The implementer and task-reviewer prompts are unchanged.
What must survive
Same as executing-plans. Each deletion becomes a decision card in the implementation notes and a Ruling: line in the ledger so it appears in the final “Rulings I made” roll-up.

The Text

The wording below is the deliverable. The plan may tighten phrasing but not change the procedure, the placement, or the “name what fails” test.

overlays/writing-plans/additions.md

## mySuperpower additions — Self-Review, item 4

Add this to the Self-Review checklist after type consistency:

**4. Ablation:** For each abstraction the plan introduces — a helper,
interface, base class, config knob, wrapper, or layer — name the task that
cannot be completed without it. If no task needs it, or one direct call
site would do, replace it in the plan with the direct thing: inline the
helper's body at its one caller, name the one implementation instead of
the interface, write the value instead of the knob. The plan still shows
that concrete code. A plan gets no credit for structure it will not use.

overlays/executing-plans/additions.md

## mySuperpower additions — ablation pass before finishing

After all tasks are complete and verified, and before invoking
finishing-a-development-branch, run one ablation pass over the branch:

1. List every abstraction the branch added: helpers, interfaces, base
   classes, config knobs, wrappers, layers, indirection of any kind.
2. For each one, replace it with the direct thing — inline the single-use
   helper, call the one implementation, write the never-changing value —
   and run the full test suite. Behavior stays; only the layer goes.
3. Name what failed: a test, a spec requirement, or a second caller that
   now has nothing to call. "It might be useful later" is not a failure.
4. If something failed, restore the abstraction and move on. If nothing
   failed, commit the removal.
5. Record each removal, and each restore with its reason, as a decision
   card in the implementation notes.

Run this once, at the end. Earlier tasks build scaffolding that later
tasks consume; ablating per task removes it before its consumer exists.

overlays/subagent-driven-development/additions.md

## mySuperpower additions — ablation pass before the final review

Once every task's ledger line reads `complete` — including
`complete (... parked)` after a tripped breaker — and before running
`scripts/review-package` for the final review, the controller runs one
ablation pass over the branch itself. No subagent:

1. List every abstraction the branch added: helpers, interfaces, base
   classes, config knobs, wrappers, layers, indirection of any kind.
2. For each one, replace it with the direct thing — inline the single-use
   helper, call the one implementation, write the never-changing value —
   and run the full test suite. Behavior stays; only the layer goes.
3. Name what failed: a test, a spec requirement, or a second caller that
   now has nothing to call. "It might be useful later" is not a failure.
4. If something failed, restore the abstraction and move on. If nothing
   failed, commit the removal. The review package diffs MERGE_BASE..HEAD,
   so an uncommitted removal is invisible to the final reviewer.
5. Record each removal, and each restore with its reason, as a decision
   card in the implementation notes and a `Ruling:` line in the ledger.

The final reviewer then reviews the ablated branch. Run this once, at the
end; per-task ablation removes scaffolding before its consumer exists.

Error Handling

Deleting something that was needed

The pass is guarded by the test suite, and the restore branch is in the published text (step 4), not only here. A removal that turns a test red is restored, and the abstraction is kept with its reason recorded. A removal that stays green but breaks an untested requirement is not caught by this pass. The existing watch-it-fail rule proves a supplied test is sensitive to its implementation; it does not prove every requirement has a test. That gap is the same one every other change on the branch already lives with, and step 3 asks for a spec requirement by name so the controller checks the spec, not only the suite.

Ablating the plan into vagueness

Cutting an abstraction from a plan must not cut the concrete code that replaces it. The writing-plans item says “one direct call site would do”: the plan then shows that call site. The existing placeholder scan runs before this item and still applies after it.

Overlay text drifting from the upstream section it targets

All three additions are appended, not spliced, so an upstream rename of “Self-Review” or “Step 3” leaves the text present but pointing at a stale name. The build’s replaces entries with required: true are the existing mechanism for catching that, and no new required replace is added here because none of the three additions depends on a literal upstream string.

Owner decision: no behavioral eval

The project guidelines require adversarial pressure testing for skill-content changes. That rule is written for pull requests to upstream. This change is fork-local, lives only in overlays, adds a step rather than rewording tuned content, and the owner requested it from a gap they hit. Prior fork overlay changes have shipped on the same basis. This is an explicit owner override, confirmed at spec sign-off, not an oversight. If the owner wants an eval, the plan adds one Drill scenario per skill in evals/ before the overlay edits.

Non-Goals

  • No changes to files under skills/.
  • No per-task ablation.
  • No change to the implementer or task-reviewer prompt templates.
  • No mention of harness-specific commands such as /simplify in the skill text.
  • No ablation line for brainstorming. It already says “YAGNI ruthlessly” at design time.

Self-Review

  • Placeholders: none. The three text blocks are final wording.
  • Consistency: all three blocks share the same four-step procedure and the same “name what fails” test. The SDD block adds only the ledger line, which matches that skill’s existing Rulings roll-up.
  • Scope: three files, one plan.
  • Ambiguity: Codex round 1 found five: “remove” undefined, no restore branch in the published text, no commit step before the SDD review package, an SDD trigger that skipped parked-finding completions, and an eval exemption stated as fact rather than as an owner decision. All five are fixed above.
